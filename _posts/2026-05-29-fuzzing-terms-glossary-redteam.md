# Fuzzing 관련 용어 정리

fuzzing을 공부하면서 자주 보이는 용어들을 따로 정리했다.  
처음에는 단어들이 다 비슷해 보여서 헷갈렸는데, 결국 핵심은 “입력을 어떻게 만들고, 프로그램이 어디까지 실행됐는지 어떻게 보고, 발견한 오류를 어떻게 분석할 것인가”로 이어진다.

레드팀 관점에서는 fuzzing이 단순한 테스트가 아니라, 공격자가 조작할 수 있는 입력 지점에서 취약점 후보를 찾는 과정으로 연결될 수 있다.  
특히 파일 파서, 네트워크 프로토콜, API 입력 처리 로직처럼 외부 입력을 많이 받는 부분은 fuzzing으로 확인해 볼 가치가 크다.

---

# Fuzzing

프로그램에 여러 가지 입력값을 자동으로 넣어 보면서 크래시, 멈춤, 메모리 오류, 비정상 동작 같은 버그를 찾는 테스트 기법

ex) 이미지 뷰어에 정상 PNG 파일뿐만 아니라 일부러 깨뜨린 PNG 파일을 계속 넣어 봄 → 프로그램이 죽거나 이상하게 동작하는지 확인

사람이 직접 이상한 입력을 하나씩 만들기는 어렵기 때문에 fuzzer가 자동으로 수많은 입력을 만들어 테스트함

특히

1. 파일 파서
2. 압축 해제 프로그램
3. 이미지/영상 처리 라이브러리
4. 브라우저 엔진
5. 네트워크 프로토콜 처리 코드
6. API 입력 처리 로직

같이 외부 입력을 많이 받는 프로그램에서 중요함

레드팀 관점:  
공격자가 조작할 수 있는 입력값을 계속 바꿔 보면서 프로그램이 어디서 무너지는지 확인할 수 있기 때문에, 취약점 발굴의 시작점으로 볼 수 있음

---

# Fuzzer

fuzzing을 자동으로 수행하는 도구

ex) AFL++, libFuzzer, Jackalope, Honggfuzz 같은 도구가 입력을 만들고, 대상 프로그램을 실행하고, 크래시가 났는지 확인함

fuzzer가 하는 일

1. 입력값을 만든다
2. 대상 프로그램에 넣는다
3. 실행 결과를 확인한다
4. 새로운 코드 경로를 찾으면 그 입력을 저장한다
5. 크래시가 나면 재현 가능한 입력을 남긴다

Fuzzing은 방법이고, Fuzzer는 그 방법을 실제로 수행하는 도구라고 이해하면 됨

---

# Target

테스트할 프로그램 또는 함수

ex) PNG 파일을 읽는 프로그램을 fuzzing한다면 그 PNG 파서가 target이 됨

target은 크게 두 가지로 나눌 수 있음

1. 실행 파일 전체
2. 특정 라이브러리 함수

레드팀 관점:  
target을 잘 고르는 것이 중요함. 외부 입력을 받는 부분, 복잡한 파싱을 하는 부분, 과거에 취약점이 자주 나왔던 부분을 우선 보는 것이 좋음

---

# Seed / Corpus

fuzzer가 처음 참고할 정상 입력 모음

ex) PNG 파서를 테스트한다면 정상적인 PNG 파일 몇 개를 seed로 넣어 둠

아무 입력이나 넣으면 프로그램이 초반에서 바로 거부할 수 있음.  
그래서 어느 정도 정상적인 입력을 seed로 주고, fuzzer가 그것을 조금씩 변형하면서 더 깊은 코드까지 들어가게 만듦

Seed와 Corpus를 나누면 이렇게 볼 수 있음

1. Seed: 처음 시작할 때 넣는 기본 입력
2. Corpus: fuzzing을 진행하면서 저장되고 발전하는 입력 모음

좋은 seed의 특징

1. 너무 크지 않음
2. 정상적으로 처리됨
3. 다양한 기능을 실행시킴
4. target의 여러 코드 경로를 건드림

---

# Mutation

입력을 변형하는 것

ex) 정상 파일의 일부 바이트를 바꾸거나, 길이를 늘리거나, 특정 값을 0이나 큰 숫자로 바꿈

예시

1. `hello` → `hEllo`
2. 길이값 `10` → `999999`
3. 파일 중간 일부 삭제
4. 특정 바이트 반복 삽입
5. 헤더 값 변경

Mutation-based fuzzing은 기존 입력을 망가뜨리면서 버그를 찾는 방식임

레드팀 관점:  
공격자가 실제로 입력값을 조작하는 방식과 비슷함. “여기를 바꾸면 프로그램이 이상하게 반응하지 않을까?”를 자동화한 느낌에 가까움

---

# Coverage

실행된 코드 범위

ex) 입력 A는 10줄만 실행했지만, 입력 B는 새로운 if문 안쪽까지 들어가서 30줄을 실행함

fuzzer는 coverage를 보고 이런 판단을 할 수 있음

1. 이 입력이 새로운 코드 경로를 열었는가?
2. 더 깊은 함수까지 들어갔는가?
3. 기존 입력과 다른 동작을 만들었는가?

좋은 fuzzer는 단순히 랜덤 입력만 넣는 것이 아니라, coverage를 보고 더 의미 있는 입력을 남김

---

# Coverage-guided Fuzzing

coverage 정보를 활용해서 더 많은 코드 경로를 실행하도록 입력을 발전시키는 fuzzing 방식

ex) 어떤 입력이 새로운 함수까지 도달했다면, fuzzer가 그 입력을 저장하고 다시 변형해서 더 깊이 들어가려고 함

대표 도구

1. AFL++
2. libFuzzer
3. Honggfuzz
4. Jackalope

레드팀 관점:  
공격 표면을 넓게 훑는 데 유용함. 단순히 프로그램이 죽는지 보는 것이 아니라, 새로운 실행 경로를 계속 찾아가면서 숨은 버그를 찾는 방식이기 때문임

---

# Crash

프로그램 비정상 종료

ex) Segmentation fault, abort, access violation 같은 오류로 프로그램이 죽음

fuzzing에서 crash는 중요한 신호임.  
단순 버그일 수도 있지만, 메모리 오염이나 권한 탈취 가능성이 있는 취약점의 시작일 수도 있음

분석할 때 볼 것

1. 같은 입력으로 재현되는가?
2. 어느 함수에서 죽었는가?
3. 메모리 오류가 있는가?
4. 보안 영향도가 있는가?
5. exploit 가능성이 있는가?

레드팀 관점:  
crash 자체가 바로 취약점이라는 뜻은 아니지만, 재현 가능하고 원인이 명확하다면 BugBounty 보고서나 PoC 작성으로 이어질 수 있음

---

# Hang

프로그램이 종료되지 않고 멈추거나 너무 오래 실행되는 상태

ex) 특정 입력을 넣었더니 CPU를 계속 사용하면서 끝나지 않음

Crash가 프로그램이 죽는 것이라면, Hang은 프로그램이 계속 붙잡혀 있는 상태에 가까움

보안적으로는 DoS 취약점으로 이어질 수 있음

ex) 서버가 특정 요청 하나 때문에 계속 멈춰 있으면 정상 사용자가 서비스를 이용하지 못할 수 있음

해결

1. 입력 크기 제한
2. 반복 횟수 제한
3. timeout 설정
4. 비정상적으로 복잡한 입력 거부
5. 예외 처리 추가

---

# Harness

특정 함수나 API를 fuzzer가 호출할 수 있게 만든 테스트 코드

ex) 이미지 파서 라이브러리의 `parse_png()` 함수만 fuzzing하고 싶을 때, 입력 데이터를 받아 그 함수를 호출하는 작은 코드를 작성함

왜 필요한가?

1. 프로그램 전체를 실행하는 것보다 빠름
2. 원하는 기능만 집중적으로 테스트할 수 있음
3. 반복 실행이 쉬움
4. 크래시 재현이 편해짐

레드팀 관점:  
취약해 보이는 기능을 좁혀서 반복적으로 테스트할 수 있기 때문에, 공격 표면을 더 효율적으로 검증할 수 있음

---

# Sanitizer

메모리 오류 등을 잡아주는 검사 도구

ex) AddressSanitizer를 사용하면 buffer overflow, use-after-free 같은 메모리 오류를 더 잘 찾을 수 있음

fuzzer만 사용하면 프로그램이 바로 죽지 않는 오류는 놓칠 수 있음.  
sanitizer를 함께 쓰면 겉으로는 멀쩡해 보여도 내부에서 잘못된 메모리 접근이 발생했는지 확인할 수 있음

대표 예시

1. AddressSanitizer: 잘못된 메모리 접근 탐지
2. UndefinedBehaviorSanitizer: 정의되지 않은 동작 탐지
3. MemorySanitizer: 초기화되지 않은 메모리 사용 탐지
4. ThreadSanitizer: 스레드 관련 오류 탐지

레드팀 관점:  
sanitizer는 취약점 후보를 더 빨리 드러나게 해 주는 보조 도구라고 볼 수 있음

---

# File Parser

파일 내용을 읽어서 프로그램이 이해할 수 있는 구조로 바꿔주는 부분

ex) PNG 파일을 읽어서 이미지 크기, 색상 정보, 픽셀 데이터 등을 해석하는 코드

파일 파서가 위험한 이유

1. 외부에서 받은 파일을 처리함
2. 파일 형식이 복잡한 경우가 많음
3. 길이값, 압축 데이터, 헤더 정보 등을 잘못 처리하면 오류가 생김
4. C/C++로 작성된 경우 메모리 취약점으로 이어질 수 있음

예시

1. 이미지 파서
2. PDF 파서
3. ZIP 압축 해제 코드
4. 문서 파일 파서
5. 미디어 파일 파서

레드팀 관점:  
파일 하나만 열었는데 프로그램이 죽거나 코드 실행으로 이어지는 취약점이 나올 수 있기 때문에, fuzzing 대상이 되기 좋음

---

# Buffer Overflow

프로그램이 준비해 둔 메모리 공간보다 더 많은 데이터를 넣어서 옆 메모리까지 덮어써 버리는 취약점

ex) 8바이트만 저장할 수 있는 칸에 더 큰 데이터를 넣음 → 주변 메모리 침범 → 프로그램 오류, 크래시, 권한 탈취 가능

특히 C/C++처럼 메모리를 직접 다루는 언어에서 자주 발생

해결

1. 입력 가능한 크기를 제한하기
2. 안전한 함수 사용하기
3. 경계 검사 추가하기
4. 컴파일러 보호 기법 사용하기
5. sanitizer로 테스트하기

최근에는 보호기법 때문에 예전보다 exploit이 훨씬 어려워짐

1. ASLR: 메모리 주소를 실행할 때마다 랜덤하게 바꾸는 보호기법
2. Canary: 스택 버퍼 오버플로우를 탐지하는 보호기법
3. NX: 실행하면 안 되는 메모리 영역에서는 코드를 실행하지 못하게 막는 보호기법

하지만 보호기법이 있다고 해서 취약점이 사라지는 것은 아님.  
공격자는 정보 유출, ROP, 보호기법 우회 등을 통해 exploit 가능성을 계속 찾기 때문에, fuzzing으로 입력 처리 오류를 조기에 찾는 것이 중요함

---

# Use-After-Free

이미 해제한 메모리를 다시 사용하는 취약점

ex) 프로그램이 어떤 객체를 free한 뒤에도 그 객체를 가리키는 포인터를 계속 사용함 → 잘못된 메모리 접근 → 크래시 또는 코드 실행 가능성

특히 브라우저, PDF 리더, 복잡한 C/C++ 프로그램에서 자주 언급됨

해결

1. 해제한 포인터를 다시 사용하지 않기
2. free 후 포인터를 NULL로 초기화하기
3. 객체 생명주기 관리하기
4. sanitizer로 테스트하기

레드팀 관점:  
Use-After-Free는 exploit으로 이어질 가능성이 있는 중요한 메모리 취약점 중 하나라서, crash가 발생하면 원인을 꼭 확인해야 함

---

# Out-of-Bounds Read / Write

정해진 메모리 범위를 벗어나서 읽거나 쓰는 취약점

ex) 배열 크기는 10인데 11번째, 12번째 값을 읽거나 씀

나누면

1. Out-of-Bounds Read: 범위 밖 메모리를 읽음
2. Out-of-Bounds Write: 범위 밖 메모리에 씀

Out-of-Bounds Read는 정보 유출로 이어질 수 있고, Out-of-Bounds Write는 메모리 오염이나 코드 실행으로 이어질 수 있음

해결

1. 배열 인덱스 검사
2. 길이값 검증
3. 입력 크기 제한
4. sanitizer 사용

---

# Integer Overflow

정수 계산 결과가 표현 가능한 범위를 넘어가서 이상한 값으로 바뀌는 문제

ex) 아주 큰 숫자끼리 더했더니 값이 작아지거나 음수처럼 처리됨

보안적으로 위험한 이유

1. 메모리 할당 크기가 잘못 계산될 수 있음
2. 길이 검사를 우회할 수 있음
3. buffer overflow로 이어질 수 있음

예시

```c
int size = width * height;
```

width와 height가 너무 크면 계산 결과가 overflow되어 실제보다 작은 size가 만들어질 수 있음

해결

1. 계산 전 범위 검사
2. 안전한 정수 타입 사용
3. overflow 검사 함수 사용
4. 비정상적으로 큰 입력 거부

---

# Triage

fuzzing으로 발견한 crash나 hang을 분류하고 우선순위를 정하는 과정

ex) crash가 100개 나왔을 때, 전부 다른 버그인지 같은 원인인지 확인하고 보안 영향도가 큰 것부터 분석함

확인할 것

1. 재현 가능한가?
2. 같은 원인의 중복 crash인가?
3. 어느 위치에서 발생했는가?
4. 보안 영향도가 있는가?
5. 보고할 가치가 있는가?

레드팀 관점:  
fuzzing 결과를 그대로 취약점이라고 할 수는 없음. triage를 통해 의미 있는 crash를 골라내야 실제 보고서나 PoC로 이어질 수 있음

---

# Reproducer

crash나 hang을 다시 발생시킬 수 있는 입력 파일 또는 실행 방법

ex) 특정 깨진 PNG 파일을 넣으면 항상 프로그램이 죽는다면, 그 PNG 파일이 reproducer가 됨

중요한 이유

1. 버그를 검증할 수 있음
2. 개발자에게 전달할 수 있음
3. 패치 후 해결 여부를 확인할 수 있음
4. BugBounty 보고서의 근거가 됨

레드팀 관점:  
재현이 안 되는 취약점은 설득력이 떨어짐. 그래서 fuzzing 결과를 정리할 때 reproducer를 남기는 것이 매우 중요함

---

# PoC

Proof of Concept의 줄임말로, 취약점이 실제로 존재한다는 것을 보여주는 증명 코드 또는 재현 방법

ex) 특정 입력 파일을 넣으면 프로그램이 crash나는 것을 보여주는 스크립트나 파일

PoC에 들어가면 좋은 것

1. 취약한 버전
2. 실행 방법
3. 입력 파일
4. 발생 결과
5. 보안 영향도
6. 재현 화면 또는 로그

레드팀 관점:  
fuzzing으로 crash를 찾은 뒤, 그것이 보안적으로 의미 있는지 보여주려면 PoC 정리가 필요함

---

# AFL++

AFL을 발전시킨 대표적인 coverage-guided fuzzer

ex) C/C++ 프로그램을 컴파일할 때 instrumentation을 넣고, 실행 중 coverage를 보면서 새로운 입력을 계속 발전시킴

특징

1. coverage-guided fuzzing
2. 빠른 mutation
3. crash/hang 자동 저장
4. 다양한 컴파일 모드 지원
5. 실전 fuzzing에서 많이 사용됨

기본 흐름

1. target 프로그램을 AFL++용 컴파일러로 컴파일
2. seed 입력 준비
3. `afl-fuzz` 실행
4. crashes, hangs 결과 확인
5. crash 재현 및 분석

레드팀 관점:  
입문용으로도 좋고 실전성도 높은 도구라서, fuzzing을 처음 실습한다면 AFL++부터 잡는 것이 좋아 보임

---

# libFuzzer

LLVM에서 제공하는 in-process coverage-guided fuzzer

in-process는 대상 프로그램을 매번 새로 실행하는 것이 아니라, 같은 프로세스 안에서 특정 함수를 계속 호출하는 방식에 가까움

ex) 특정 라이브러리 함수에 입력 데이터를 바로 넣고 반복 테스트함

특징

1. 함수 단위 fuzzing에 적합
2. 빠름
3. sanitizer와 함께 쓰기 좋음
4. harness 작성이 중요함

레드팀 관점:  
소스코드가 있거나 특정 API를 직접 테스트할 수 있을 때 유용함. 프로그램 전체보다 취약해 보이는 함수 하나를 집중적으로 때려볼 수 있음

---

# Jackalope

Google Project Zero에서 공개한 coverage-guided fuzzer

특히 소스코드가 없는 black-box binary 대상 fuzzing에 초점이 있음

ex) Windows/macOS/Linux/Android 바이너리를 대상으로 coverage를 보면서 fuzzing할 수 있음

특징

1. black-box binary fuzzing 가능
2. coverage-guided 방식
3. custom mutator 지원
4. 복잡한 target에 맞게 커스터마이징 가능

레드팀 관점:  
상용 프로그램처럼 소스코드가 없는 대상을 분석해야 할 때 의미가 있음. 실제 공격자 관점의 바이너리 분석과 fuzzing을 연결해 볼 수 있는 도구라고 느껴짐

---

# Honggfuzz

보안 연구에 자주 언급되는 feedback-driven fuzzer

실행 중 얻은 피드백을 바탕으로 더 의미 있는 입력을 만들어 가는 방식

특징

1. coverage 기반 피드백 사용
2. 다양한 실행 방식 지원
3. sanitizer와 함께 사용 가능
4. 보안 취약점 탐색에 적합

레드팀 관점:  
AFL++와 함께 비교해 보기 좋은 도구임. 같은 target을 여러 fuzzer로 테스트하면 서로 다른 crash를 찾을 수도 있음

---

# OSS-Fuzz

Google에서 운영하는 오픈소스 프로젝트 대상 continuous fuzzing 인프라

fuzzer 하나라기보다는, 여러 오픈소스 프로젝트를 계속 fuzzing해 주는 시스템에 가까움

특징

1. 지속적인 fuzzing
2. 오픈소스 프로젝트 대상
3. libFuzzer, AFL++, Honggfuzz 등과 연계 가능
4. 발견된 버그를 개발자에게 알려줌

레드팀 관점:  
직접 공격 도구라기보다는 “보안 테스트를 장기적으로 자동화하는 방식”을 이해하는 데 좋음. 실무에서는 fuzzing을 한 번 돌리고 끝내는 것이 아니라, 코드가 바뀔 때마다 계속 돌리는 구조가 중요하다는 점을 보여줌

# 정리

fuzzing 관련 용어들은 처음에는 많아 보이지만, 흐름으로 보면 단순해진다.

1. Target을 정한다
2. Seed/Corpus를 준비한다
3. Fuzzer가 Mutation을 통해 입력을 바꾼다
4. Coverage를 보면서 더 깊은 코드 경로를 찾는다
5. Crash나 Hang이 나오면 저장한다
6. Sanitizer로 메모리 오류를 더 잘 잡는다
7. Reproducer와 PoC로 정리한다
8. Triage를 통해 보고할 가치가 있는 취약점인지 판단한다

결국 fuzzing은 “이상한 입력을 많이 넣어 보는 것”에서 시작하지만, 실제로는 취약점 후보를 찾고 분석하고 재현하는 과정까지 이어진다.  
레드팀을 목표로 한다면 fuzzing은 단순 테스트 기법이 아니라, 공격 표면을 넓게 탐색하고 숨은 버그를 발견하는 중요한 방법 중 하나로 익혀 둘 필요가 있다고 느꼈다.
