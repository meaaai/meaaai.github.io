# 웹 보안 기초: SQL Injection, XSS, CSRF

웹 보안에서 가장 자주 나오는 대표적인 취약점 3가지는 다음과 같다.

- SQL Injection
- XSS
- CSRF

셋 다 이름은 다르지만, 공통점이 있다.

> **원래는 "데이터"로 다뤄져야 할 것이, 코드나 권한처럼 오용되는 순간 문제가 생긴다.**

---

# SQL Injection (SQL 인젝션, SQLi)

## SQL Injection이란?

SQL Injection은 **웹사이트가 사용자 입력값을 그대로 SQL 문에 붙여서 실행할 때**, 공격자가 그 입력값을 조작해 **원래 의도와 다른 데이터베이스 명령이 실행되게 만드는 취약점**이다.

쉽게 말하면,

- 원래 개발자는 아이디와 비밀번호를 확인하려고 했다.
- 공격자는 입력창에 조작된 값을 넣는다.
- 그러면 DB가 이를 **다른 의미의 SQL 문법으로 해석**하게 된다.

즉, 사용자가 넣어야 할 것은 단순한 "값"인데, 공격자는 거기에 **SQL 문법 일부를 끼워 넣어서** 서버가 이를 코드처럼 실행하게 만드는 것이다.

> 사용자 입력이 DB 쿼리에 들어가는 모든 곳은 잠재적인 공격 대상이 될 수 있다.

예를 들어, 아이디 입력창에 악의적인 값을 넣으면 서버는 이를 단순 입력값이 아니라 코드처럼 해석할 수 있고, 그 결과 항상 참이 되는 조건이나 의도하지 않은 조건으로 바뀐 쿼리가 실행될 수 있다.

## 왜 "Injection"이라고 부를까?

`Injection`은 말 그대로 **주입**이라는 뜻이다.

즉, 사용자가 단순한 값만 넣어야 하는 입력창에 공격자가 **SQL 문법을 주입**하는 것이다.  
결과적으로 서버는 입력값을 데이터가 아니라 **코드처럼 해석**하게 된다.

## 무슨 문제가 발생할까?

### 1. 로그인 우회

정상 비밀번호를 몰라도 로그인되는 상황이 발생할 수 있다.

### 2. 데이터 열람

회원 정보, 게시글, 주문 내역 같은 DB 정보를 조회할 수 있다.

### 3. 데이터 변경

비밀번호 수정, 게시글 수정, 권한 변경 등이 가능해질 수 있다.

### 4. 데이터 삭제

테이블 내용 삭제나 서비스 마비 같은 심각한 피해가 발생할 수 있다.

### 5. 관리자 권한 획득

권한 관련 로직이 취약하면 관리자 권한으로 동작하게 만들 수도 있다.

## 어떻게 막을까?

### 1. Prepared Statement / Parameterized Query 사용

가장 핵심적인 방어 방법이다.

사용자 입력을 SQL 문법의 일부가 아니라 **순수한 값(parameter)** 으로 처리하게 만든다.

예시:

```python
cursor.execute("SELECT * FROM users WHERE id = %s", (user_id,))
```

이렇게 하면 `user_id`에 이상한 문자열이 들어와도 SQL 구조 자체를 바꾸기 어려워진다.

이게 **가장 정석적인 방어 방법**이다.

### 2. 문자열 이어붙이기 금지

아래와 같은 방식은 매우 위험하다.

```python
query = "SELECT * FROM users WHERE id = '" + user_id + "'"
```

이건 가장 흔한 실수이자, 가장 위험한 패턴 중 하나다.

### 3. 입력값 검증

예를 들면 다음과 같다.

- 숫자만 들어와야 하는 곳은 숫자만 허용
- 아이디는 허용된 문자만 받기
- 길이 제한
- 화이트리스트 검증

다만 이건 **보조 방어책**일 뿐이다.  
좋은 방법이지만 **이것만으로는 충분하지 않다.**

### 4. 에러 메시지 숨기기

DB 에러를 사용자에게 그대로 보여주면 공격자에게 많은 힌트를 주게 된다.

사용자에게는 일반적인 에러 메시지만 보여주고, 상세한 에러는 서버 로그에만 남기는 것이 좋다.

### 5. 최소 권한 원칙

DB 계정에는 꼭 필요한 권한만 부여해야 한다.

예를 들어 조회만 필요한 기능인데 삭제나 수정 권한까지 있다면, 공격 성공 시 피해 규모가 훨씬 커진다.

### 6. ORM 사용 시에도 주의

ORM을 사용하면 도움이 되지만, raw SQL을 문자열로 직접 조합하면 여전히 취약해질 수 있다.

즉, **도구보다 사용 습관이 더 중요하다.**

## 필터링만 하면 안 될까?

초보자가 많이 하는 생각이다.

- "작은따옴표만 막으면 되는 거 아니야?"
- "특수문자 차단하면 끝 아닌가?"

결론부터 말하면 **안 된다.**

이유는 다음과 같다.

- DB마다 문법이 다르다.
- 우회 방법이 많다.
- 인코딩, 대소문자, 공백 등으로 변형이 가능하다.
- 필터링 누락 지점이 생길 수 있다.

그래서 보안에서는 보통 **"막아야 할 문자열 목록"을 관리하는 것보다, 애초에 SQL 구조와 입력값을 분리하는 것**을 훨씬 더 중요하게 본다.

즉, 핵심은 **parameterized query**다.

# XSS (Cross-Site Scripting)

## XSS란?

XSS는 **사용자 입력이 브라우저에서 코드(JavaScript)로 실행되는 취약점**이다.

사용자가 글을 쓰면 원래는 단순한 텍스트로 보여야 한다.  
하지만 취약한 경우 사용자의 입력값이 HTML 또는 JavaScript 코드로 실행될 수 있다.

즉, 서버 입장에서는 "그냥 글"이라고 생각하고 저장하거나 출력했는데, 브라우저는 그걸 **코드로 해석해서 실행**해 버리는 것이다.

## XSS가 발생하면 공격자는?

- 쿠키 탈취
- 계정 탈취
- 사용자 행동 조작
- 악성 스크립트 실행

즉, XSS는 **사용자 브라우저를 공격하는 취약점**이다.

## 핵심 원리: SQL Injection과 비교

| 구분 | SQL Injection | XSS |
| --- | --- | --- |
| 실행 위치 | 서버(DB) | 브라우저 |
| 문제 | SQL로 실행됨 | JavaScript로 실행됨 |
| 본질 | 입력이 코드로 해석됨 | 입력이 코드로 해석됨 |

| 구분 | SQLi | XSS |
| --- | --- | --- |
| 공격 대상 | 서버(DB) | 사용자(브라우저) |
| 목적 | 데이터 탈취 | 쿠키 탈취, 계정 해킹 |
| 사용 언어 | SQL | JavaScript |
| 발생 위치 | 서버 쿼리 처리 | 웹 페이지 출력 |
| 피해 대상 | 서비스 전체 | 특정 사용자 |

둘 다 본질은 같다.

> **데이터를 코드처럼 실행해 버린 것**

## XSS 종류 3가지

### 1. Stored XSS (저장형) - 가장 위험

서버에 저장되는 형태다.

예시:

- 게시판 글
- 댓글
- 프로필

흐름은 다음과 같다.

1. 공격자가 악성 코드를 작성한다.
2. 그 코드가 DB에 저장된다.
3. 다른 사용자가 페이지를 열면 해당 코드가 실행된다.

### 2. Reflected XSS (반사형)

입력값이 서버 응답에 바로 포함되는 형태다.

예시:

```text
검색창 -> 결과 페이지
```

흐름은 다음과 같다.

1. 공격자가 악성 스크립트가 포함된 URL을 만든다.
2. 피해자에게 해당 링크를 보낸다.
3. 피해자가 클릭하면 스크립트가 바로 실행된다.

### 3. DOM-based XSS

서버가 아니라 **브라우저의 JavaScript 코드 문제**로 발생한다.

서버는 안전한 응답을 보냈더라도, 클라이언트 측 JS가 DOM을 조작하는 과정에서 취약점이 생길 수 있다.

흐름은 다음과 같다.

- 사용자 입력
- JavaScript 처리
- DOM에 삽입
- 스크립트 실행

## XSS는 어떻게 막을까?

> **출력할 때 반드시 escape(인코딩) 해야 한다.**

### 1. Output Encoding (출력 시 인코딩)

위험한 문자를 안전한 문자 표현으로 바꿔서, 브라우저가 이를 코드가 아닌 **그냥 텍스트**로 해석하게 만드는 방법이다.

| 문자 | 변환 |
| --- | --- |
| `<` | `&lt;` |
| `>` | `&gt;` |
| `"` | `&quot;` |
| `'` | `&#39;` |

### 2. 입력 검증

사용자가 넣은 값이 허용된 형식인지 확인하는 방법이다.

예를 들면,

- 나이 입력칸: 숫자만 허용
- 아이디: 영문/숫자만 허용

하지만 이것 역시 **보조 수단**일 뿐이다.  
우회 방법이 너무 많기 때문에, 입력 검증만으로는 XSS를 막을 수 없다.

### 3. Content Security Policy (CSP)

브라우저에게 **어떤 JavaScript만 실행할 수 있는지 제한**하는 보안 정책이다.

### 4. HttpOnly 쿠키

JavaScript가 쿠키를 읽지 못하게 막는다.

그래서 XSS가 발생하더라도 쿠키 탈취를 어렵게 만들 수 있다.

### 5. DOM 조작 시 안전한 함수 사용

위험한 예:

```javascript
element.innerHTML = user_input;
```

안전한 예:

```javascript
element.textContent = user_input;
```

`textContent`는 입력값을 HTML로 해석하지 않기 때문에 훨씬 안전하다.

## 중요도 정리

| 방법 | 중요도 |
| --- | --- |
| Output Encoding | ⭐⭐⭐⭐⭐ |
| CSP | ⭐⭐⭐ |
| HttpOnly | ⭐⭐⭐ |
| 입력 검증 | ⭐⭐ |

## 절대 하면 안 되는 것

### "필터링으로 막기"

예를 들어 이런 식이다.

```javascript
if (input.includes("<script>")) block;
```

이 방식은 **결국 뚫린다.**

XSS는 입력을 단순 필터링해서 막는 문제가 아니라, **출력할 때 반드시 escape 해야 막을 수 있는 취약점**이다.

# CSRF (Cross-Site Request Forgery)

## CSRF란?

CSRF는 **사용자가 로그인된 상태라는 점을 악용해서, 사용자가 원하지 않는 요청을 서버로 보내게 만드는 공격**이다.

쉽게 말하면,

- 사용자는 어떤 사이트에 이미 로그인되어 있다.
- 공격자는 사용자를 속여서 악성 페이지를 열게 하거나 특정 행동을 유도한다.
- 그러면 브라우저가 자동으로 로그인 쿠키를 함께 보내고,
- 서버는 그 요청을 **정상 사용자의 요청이라고 착각**하게 된다.

즉, 공격자가 직접 로그인한 것이 아니라 **피해자의 권한을 빌려 요청을 위조하는 것**이다.

## 왜 "Forgery"라고 부를까?

`Forgery`는 **위조**라는 뜻이다.

즉, 사용자가 실제로 원해서 보낸 요청이 아닌데도, 서버 입장에서는 **정상 사용자가 보낸 진짜 요청처럼 보이게 만드는 것**이다.

그래서 이름이 **Cross-Site Request Forgery**다.

- `Cross-Site`: 다른 사이트를 통해
- `Request`: 요청을 보내고
- `Forgery`: 그 요청을 정상 요청처럼 위조하는 것

## 어떤 문제가 발생할까?

### 1. 비밀번호 변경

사용자가 모르는 사이 계정 비밀번호가 바뀔 수 있다.

### 2. 이메일 변경

복구 이메일이 공격자 주소로 바뀌면 계정 탈취로 이어질 수 있다.

### 3. 게시글 작성 또는 삭제

사용자 권한으로 원하지 않는 글이 작성되거나 삭제될 수 있다.

### 4. 결제 또는 송금 요청

금융 서비스나 쇼핑몰에서는 더 큰 피해로 이어질 수 있다.

### 5. 관리자 기능 오용

관리자가 로그인된 상태에서 공격을 당하면 권한이 큰 만큼 피해도 커진다.

## XSS와 CSRF는 어떻게 다를까?

헷갈리기 쉬운데, 둘은 공격 방식이 다르다.

| 구분 | XSS | CSRF |
| --- | --- | --- |
| 본질 | 입력이 코드로 실행됨 | 사용자의 요청이 위조됨 |
| 공격 대상 | 사용자 브라우저 | 서버의 요청 처리 로직 |
| 핵심 악용 요소 | 스크립트 실행 | 로그인된 사용자 권한 |
| 대표 피해 | 쿠키 탈취, 계정 탈취 | 비밀번호 변경, 결제, 게시글 작성 |

정리하면,

- **XSS는 브라우저에서 코드를 실행시키는 공격**
- **CSRF는 사용자의 인증 상태를 악용해 요청을 보내는 공격**

이다.

## CSRF가 성립하려면?

보통 다음 조건이 필요하다.

### 1. 사용자가 로그인된 상태여야 한다

브라우저가 인증 쿠키나 세션 정보를 자동으로 보내야 한다.

### 2. 서버가 요청의 진짜 출처를 제대로 검증하지 않아야 한다

즉, 요청이 정말 사용자가 보낸 것인지 확인하는 장치가 없어야 한다.

### 3. 요청만 성공하면 동작이 수행되는 구조여야 한다

예를 들어 비밀번호 변경, 이메일 변경, 결제 요청 같은 기능이 해당된다.

## 어떻게 막을까?

### 1. CSRF Token 사용

가장 대표적이고 중요한 방어 방법이다.

서버가 사용자의 세션마다 **예측 불가능한 토큰**을 발급하고, 중요한 요청을 보낼 때 이 토큰도 함께 제출하게 만든다.

그러면 공격자는 사용자의 브라우저로 요청을 보내게 만들 수는 있어도, **정확한 토큰 값까지 맞추기는 어렵다.**

즉, 서버는 이렇게 확인할 수 있다.

- 이 요청이 로그인된 사용자 요청인가?
- 그리고 정말 우리 사이트가 만든 정상 폼에서 온 요청인가?

이게 CSRF 방어의 핵심이다.

### 2. SameSite 쿠키 설정

쿠키에 `SameSite` 속성을 설정하면, 다른 사이트에서 들어오는 요청에 대해 브라우저가 쿠키를 자동으로 보내지 않도록 제한할 수 있다.

대표적으로 다음과 같은 설정이 있다.

- `SameSite=Lax`
- `SameSite=Strict`

이 설정은 CSRF 위험을 줄이는 데 매우 유용하다.

다만 상황에 따라 서비스 동작과 충돌할 수 있으므로, 실제 환경에서는 정책을 잘 선택해야 한다.

### 3. Origin / Referer 검증

서버에서 요청 헤더의 `Origin` 또는 `Referer`를 확인해서, 요청이 정말 **우리 사이트에서 발생한 것인지** 검사할 수 있다.

이 방법은 좋은 보조 수단이지만, 환경에 따라 헤더가 없거나 불완전할 수 있어서 **토큰 방식의 대체재가 아니라 보조책**으로 보는 것이 좋다.

### 4. 중요한 작업은 재인증 요구

정말 민감한 기능이라면 비밀번호를 한 번 더 입력하게 하거나, 2차 인증을 요구하는 것이 좋다.

예를 들면 다음과 같다.

- 비밀번호 변경
- 이메일 변경
- 결제
- 출금
- 관리자 권한 변경

이렇게 하면 설령 요청 위조가 시도되더라도 피해를 줄일 수 있다.

### 5. 상태를 바꾸는 작업에 GET 사용 금지

조회만 하는 요청은 `GET`이 맞지만, 데이터 변경이 일어나는 작업은 `POST`, `PUT`, `DELETE` 등으로 분리해야 한다.

예를 들어 아래처럼 만들면 위험하다.

```text
GET /deletePost?id=10
```

이런 구조는 링크 클릭만으로도 위험한 요청이 실행될 수 있어서 좋지 않다.

즉,

- `GET`: 조회
- `POST/PUT/DELETE`: 상태 변경

원칙을 지키는 것이 중요하다.

### 6. API에서는 커스텀 헤더 전략도 활용 가능

AJAX 요청 기반 서비스에서는 서버가 특정 커스텀 헤더를 요구하게 만들고, 브라우저가 자동으로 붙이지 않는 헤더인지 확인하는 방식도 사용할 수 있다.

다만 이것도 **기본은 CSRF 토큰과 올바른 인증 정책** 위에서 보조적으로 사용하는 것이 좋다.

## 중요도 정리

| 방법 | 중요도 |
| --- | --- |
| CSRF Token | ⭐⭐⭐⭐⭐ |
| SameSite 쿠키 | ⭐⭐⭐⭐ |
| Origin/Referer 검증 | ⭐⭐⭐ |
| 재인증 | ⭐⭐⭐ |
| GET으로 상태 변경 금지 | ⭐⭐⭐ |

## 절대 하면 안 되는 것

### 1. "POST로만 보내면 안전하다"라고 생각하기

많이 하는 오해다.

`POST`라고 해서 자동으로 안전해지는 것은 아니다.  
중요한 건 **요청 방식이 아니라, 그 요청이 진짜 사용자가 보낸 것인지 검증하느냐**다.

### 2. CSRF 방어 없이 쿠키 인증만 믿기

브라우저는 쿠키를 자동으로 전송한다.  
그래서 쿠키 기반 인증만 쓰고 추가 검증이 없으면 CSRF에 취약해질 수 있다.

### 3. CORS만 설정하면 끝이라고 생각하기

이것도 흔한 착각이다.

CORS는 **다른 출처의 JavaScript 접근을 제한하는 정책**이지, CSRF를 완전히 막아주는 장치는 아니다.  
즉, CORS가 있다고 해서 CSRF가 자동으로 해결되지는 않는다.

# 정리

세 취약점은 자주 함께 언급되지만, 공격 방식과 방어 포인트는 분명히 다르다.

| 취약점 | 핵심 문제 | 공격 대상 | 대표 방어 |
| --- | --- | --- | --- |
| SQL Injection | 입력값이 SQL 코드로 해석됨 | 서버(DB) | Parameterized Query |
| XSS | 입력값이 브라우저 코드로 실행됨 | 사용자 브라우저 | Output Encoding |
| CSRF | 사용자의 권한으로 요청이 위조됨 | 서버의 요청 처리 | CSRF Token |

한 줄로 정리하면 이렇다.

- **SQL Injection**: DB가 속는다.
- **XSS**: 브라우저가 속는다.
- **CSRF**: 서버가 사용자의 요청이라고 착각한다.

보안에서는 결국 같은 원칙이 반복된다.

> **입력값을 믿지 말고, 구조를 분리하고, 출처를 검증해야 한다.**
